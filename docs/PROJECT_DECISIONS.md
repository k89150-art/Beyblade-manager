# 專案決策紀錄

最後核對日期：2026-10-29

本文件記錄目前仍有效、已被使用者確認或由正式程式與測試明確保障的長期決策。除非使用者明確改變決策，Codex 與 Claude 不得因個人偏好推翻。若決策改變，應更新本文件並記錄原因。

## D-001：深色與米色雙主題

- 網站提供深色與柔和米色主題。
- 主題選擇保存在同一瀏覽器，跨頁與重新整理後維持。
- 兩個主題使用相同 typography、結構與互動，只調整對應色彩 token。

## D-002：手機優先，桌面維持高資訊密度

- 手機須適合單手操作、無水平 overflow、保有足夠觸控範圍。
- 桌面應有效利用空間，但不能以縮小文字或塞滿資訊犧牲閱讀性。
- 收藏桌面可使用高資訊密度列表；平板與手機維持適合各自寬度的卡片呈現。

## D-003：收藏代表原裝產品

- 收藏保存原裝產品與數量，產品型號有意義。
- 原裝配置由正式型錄自動帶入；手動模式只在使用者主動切換時使用。
- 原裝配置資料服務收藏顯示與帶入，不參與主觀性能評分。

## D-004：收藏零件顯示順序

- BX／UX：上蓋 → 固鎖 → 軸心。
- CX：紋章鎖 → 主要戰刃或金屬戰刃 → 超越戰刃 → 輔助戰刃 → 固鎖 → 軸心。
- 超越戰刃與輔助戰刃相鄰，且超越在前。
- 不存在的零件直接略過，不顯示空標籤。
- BX／UX／CX 系列標籤與零件分類色彩保留；不得改回難讀的舊灰色摘要。

## D-005：額外零件庫存

- 顯示分類固定為：全部、上蓋、固鎖、軸心、CX 分件。
- CX 分件依 type 判斷，包含紋章鎖、主要戰刃、金屬戰刃、超越戰刃、輔助戰刃，不以名稱硬編碼。
- 零件類型標籤是必要資訊；數量維持靠右對齊，長名稱只能在名稱區自然換行。
- 桌面庫存維持雙欄 Grid，手機維持單欄；不得因其他頁面的卡片調整而改變欄位結構。
- 持有總數、使用中與可用必須沿用既有配置占用計算，不建立第二套規則。

## D-006：配置是自訂組合

- 配置不再要求使用者輸入產品型號；收藏與配置的語意不同。
- 舊配置資料仍須向下相容，不能因 UI 移除欄位而刪除舊資料。
- 配置列表使用 compact 設計：主要名稱、清楚的零件摘要及 `⋯` 管理選單。
- 配置卡不顯示 BX／UX／CX 裝飾性系列 Badge；不得因收藏卡保留系列識別而將它重新加回配置。
- 修改／刪除收在 `⋯` 選單，刪除保留確認流程；不恢復永久大型操作按鈕或重複零件類型標籤。

## D-007：中文名稱與型錄優先

- 主要顯示以正式中文名稱為主，英文／日文名稱與別名用於對照、搜尋與資料整理。
- 不得以臆測名稱覆蓋正式型錄；名稱合併需保留來源與相容性。
- 使用者確認的型號、繁中與英文對照基準為 `beyblade_x_model_chinese_english_2026-08-29.json`；社群翻譯不得直接覆蓋已確認名稱。
- 競賽統計的軸心維持英文縮寫。

## D-008：競賽統計只呈現客觀資料

- 競賽統計展示來源可追溯的參賽、使用與名次等客觀資訊。
- 不重新加入 Tier、主觀配置推薦、推估勝率或已退役分析頁。
- 歷史研究資料可保留於資料檔，但不能未經新決策直接成為正式 UI 功能。

## D-009：Firebase 使用者隔離

- 正式 project 為 `k89150-web-login`，資料庫為 Cloud Firestore。
- 使用者資料路徑為 `users/{uid}/appData/main`。
- Firebase UID 是資料擁有權依據；一般使用者只能讀寫自己的資料。
- 管理員介面只讀，不得變成無限制代寫工具。
- Firebase Rules、資料結構、migration 與正式資料刪除必須先提計畫並取得使用者確認。

## D-010：資料相容性優先

- 不清除或重建既有收藏、庫存、配置、歷史測試與賽事資料。
- 不任意重新命名欄位或變更資料型別。
- 跨頁 Firestore 寫入必須使用 merge 並尊重欄位所有權，避免互相覆蓋。
- 顯示層可以演進，舊資料仍必須可讀、可編輯與可刪除。

## D-011：賽事與競賽統計分工

- 賽事是使用者個人紀錄，保存於自己的 Firestore 文件。
- 競賽統計是客觀彙整頁，不是使用者個人同步資料。
- 賽事支援輪空／對方未到等不戰晉級情境，最終成績由賽程資料計算。

## D-012：舊 RTDB 保持封鎖與保留

- 舊 project：`beyblade-wangbaboa`。
- 舊 RTDB：`beyblade-wangbaboa-default-rtdb`。
- 根規則維持 `.read: false`、`.write: false`。
- 不重新開放，不刪除保留資料，不擅自 migration。

## D-013：部署需明確授權

- GitHub Pages production 由 `main` 分支根目錄提供。
- 未經使用者明確同意，不 commit、push、tag、deploy 或發布 Firebase Rules。
- 部署後必須實際檢查正式網站，不只看 CI 或命令結果。

## D-014：官方型錄與競賽統計獨立更新

- TAKARA TOMY 官方原裝配置與 MetaBeys／Beywatch 競賽統計是兩條獨立流程，不得互相覆蓋資料責任。
- 更新必須保留歷史快照、來源時間、canonical 主資料、現有 JSON schema 與已確認繁中名稱。
- 週排程是 repository 之外的運作設定。未經明確授權，Codex 與 Claude 不得執行、重建、修改或取代。

## D-015：舊收藏的手動內容優先保留

> 狀態：**已實作，待正式部署**（Phase 2，2026-10-29，本機工作樹未 commit）。正式網站在部署前仍為舊行為，尚未受到此保護。

### 已確認的正式資料政策

- 只有 `stockAutoFilled` 明確為 `true` 的收藏，才可依官方型錄自動升級。本站自身儲存的字串 `"true"` 視為同一個明確標記；其他任何值都不是。
- `stockAutoFilled` 為 `false`、缺少、無效或無法判定時，一律保留原始內容，不得自動升級，也不得補成 `true`。
- 不得只因型號唯一匹配、零件名稱相似或其他推測，把手動資料視為自動填入。
- 只有使用者明確選擇官方商品，或原資料已有明確自動填入標記，才可套用官方配置。
- 不執行任何收藏批次 migration；未來若需要升級或復原流程，必須另行核准。

### 目前程式實作（本機工作樹，待部署）

- `chooseStockProductForStoredItem()` 與 `upgradeStoredStockItem()` 先檢查 `isExplicitStockAutoFilled()`；未明確為 `true` 的收藏不選任何型錄商品、不改內容、不計入自動回寫。
- 明確自動填入的收藏：有 `stockRecordId` 時只以 recordId 識別（BX-00、CX-00 等共用型號），recordId 已不存在於型錄時不改用型號推測；沒有 recordId 的舊自動資料，只有型號唯一對應一筆商品時才升級，多筆候選一律不處理。
- 手動新增的收藏會寫入 `stockAutoFilled: "false"`；從官方型錄選擇的商品維持 `stockAutoFilled: "true"` 與 `stockRecordId`。
- 收藏列保留本頁不管理的欄位（使用者自訂欄位、`stockAutoFilled: false` 等 falsy metadata），存檔時原樣寫回。
- 管理員唯讀檢視 `user-view.js` 採相同規則，手動收藏顯示原始資料。
- 自動升級後的 `saveData()` 仍受 Phase 1 的 ready、UID、generation、readonly 防護；cache snapshot 不會觸發寫入。
- 行為測試：`tests/collection-autofill-safety.test.mjs`（實際執行 `script.js`／`user-view.js` 程式與正式型錄 JSON，含 mutation 檢查）。

### 尚未處理與殘留風險

- 部署前正式網站仍會改寫手動收藏；若部署延後，期間開啟主頁的使用者仍可能受影響。
- 過去可能已被舊版改寫的收藏，本階段不辨識、不復原；需要歷史備份才能比對，另案授權處理。
- `stockAutoFilled` 若為非字串的 truthy 值（例如數字 `1`），使用者之後手動存檔時會以字串形式寫回；值本身不會被視為 `true`。

## D-016：競賽統計歷史快照保留於 Git

- 日期化競賽統計 JSON 必須保留在 Git 專案中；新版統計新增快照，不覆蓋或自動刪除既有歷史快照。
- 不另建與現有 canonical 主資料及競賽統計契約互不相干的第二套統計資料庫。
- 現有匯入腳本尚未依此決策調整；修改腳本與對應測試必須另立任務。

## 現況與舊描述的差異

以下差異已依目前程式碼確認，不應自行「修回」舊描述：

1. **本機資料**：收藏、庫存、配置、歷史測試與賽事目前沒有 localStorage 正式副本；localStorage 只保存主題、側欄等 UI 偏好。正式業務資料由 Firestore 保存。
2. **舊 RTDB Rules**：安全封鎖是 Firebase Console 的 deployed 狀態，repository 內沒有 `database.rules.json` 可代表該舊 project。
3. **歷史分析資料**：參考 JSON 仍可能包含 meta／分析 metadata，但正式分析 UI 已退役，競賽統計仍以客觀資料為界線。
4. **Firebase 初始化**：目前多個頁面各自初始化相同 project。這是既有實作，不代表可未經任務重構。
