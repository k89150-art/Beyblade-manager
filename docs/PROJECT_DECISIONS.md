# 專案決策紀錄

最後核對日期：2026-10-29（Phase 4B 新增 D-017，4B-1 補強）

本文件記錄目前仍有效、已被使用者確認或由正式程式與測試明確保障的長期決策。除非使用者明確改變決策，Codex 與 Claude 不得因個人偏好推翻。若決策改變，應更新本文件並記錄原因。

## D-001：深色與米色雙主題

- 網站提供深色與柔和米色主題。
- 主題選擇保存在同一瀏覽器，跨頁與重新整理後維持。
- 兩個主題使用相同 typography、結構與互動，只調整對應色彩 token。

## D-002：手機優先，桌面維持高資訊密度

- 手機須適合單手操作、無水平 overflow、保有足夠觸控範圍。
- 桌面應有效利用空間，但不能以縮小文字或塞滿資訊犧牲閱讀性。
- 收藏桌面可使用高資訊密度列表；平板與手機維持適合各自寬度的卡片呈現。

## D-003：收藏代表原裝產品

- 收藏保存原裝產品與數量，產品型號有意義。
- 原裝配置由正式型錄自動帶入；手動模式只在使用者主動切換時使用。
- 原裝配置資料服務收藏顯示與帶入，不參與主觀性能評分。

## D-004：收藏零件顯示順序

- BX／UX：上蓋 → 固鎖 → 軸心。
- CX：紋章鎖 → 主要戰刃或金屬戰刃 → 超越戰刃 → 輔助戰刃 → 固鎖 → 軸心。
- 超越戰刃與輔助戰刃相鄰，且超越在前。
- 不存在的零件直接略過，不顯示空標籤。
- BX／UX／CX 系列標籤與零件分類色彩保留；不得改回難讀的舊灰色摘要。

## D-005：額外零件庫存

- 顯示分類固定為：全部、上蓋、固鎖、軸心、CX 分件。
- CX 分件依 type 判斷，包含紋章鎖、主要戰刃、金屬戰刃、超越戰刃、輔助戰刃，不以名稱硬編碼。
- 零件類型標籤是必要資訊；數量維持靠右對齊，長名稱只能在名稱區自然換行。
- 桌面庫存維持雙欄 Grid，手機維持單欄；不得因其他頁面的卡片調整而改變欄位結構。
- 持有總數、使用中與可用必須沿用既有配置占用計算，不建立第二套規則。

## D-006：配置是自訂組合

- 配置不再要求使用者輸入產品型號；收藏與配置的語意不同。
- 舊配置資料仍須向下相容，不能因 UI 移除欄位而刪除舊資料。
- 配置列表使用 compact 設計：主要名稱、清楚的零件摘要及 `⋯` 管理選單。
- 配置卡不顯示 BX／UX／CX 裝飾性系列 Badge；不得因收藏卡保留系列識別而將它重新加回配置。
- 修改／刪除收在 `⋯` 選單，刪除保留確認流程；不恢復永久大型操作按鈕或重複零件類型標籤。

## D-007：中文名稱與型錄優先

- 主要顯示以正式中文名稱為主，英文／日文名稱與別名用於對照、搜尋與資料整理。
- 不得以臆測名稱覆蓋正式型錄；名稱合併需保留來源與相容性。
- 使用者確認的型號、繁中與英文對照基準為 `beyblade_x_model_chinese_english_2026-08-29.json`；社群翻譯不得直接覆蓋已確認名稱。
- 競賽統計的軸心維持英文縮寫。

## D-008：競賽統計只呈現客觀資料

- 競賽統計展示來源可追溯的參賽、使用與名次等客觀資訊。
- 不重新加入 Tier、主觀配置推薦、推估勝率或已退役分析頁。
- 歷史研究資料可保留於資料檔，但不能未經新決策直接成為正式 UI 功能。

## D-009：Firebase 使用者隔離

- 正式 project 為 `k89150-web-login`，資料庫為 Cloud Firestore。
- 使用者資料路徑為 `users/{uid}/appData/main`。
- Firebase UID 是資料擁有權依據；一般使用者只能讀寫自己的資料。
- 管理員介面只讀，不得變成無限制代寫工具。
- Firebase Rules、資料結構、migration 與正式資料刪除必須先提計畫並取得使用者確認。

## D-010：資料相容性優先

- 不清除或重建既有收藏、庫存、配置、歷史測試與賽事資料。
- 不任意重新命名欄位或變更資料型別。
- 跨頁 Firestore 寫入必須使用 merge 並尊重欄位所有權，避免互相覆蓋。
- 顯示層可以演進，舊資料仍必須可讀、可編輯與可刪除。

## D-011：賽事與競賽統計分工

- 賽事是使用者個人紀錄，保存於自己的 Firestore 文件。
- 競賽統計是客觀彙整頁，不是使用者個人同步資料。
- 賽事支援輪空／對方未到等不戰晉級情境，最終成績由賽程資料計算。

## D-012：舊 RTDB 保持封鎖與保留

- 舊 project：`beyblade-wangbaboa`。
- 舊 RTDB：`beyblade-wangbaboa-default-rtdb`。
- 根規則維持 `.read: false`、`.write: false`。
- 不重新開放，不刪除保留資料，不擅自 migration。

## D-013：部署需明確授權

- GitHub Pages production 由 `main` 分支根目錄提供。
- 未經使用者明確同意，不 commit、push、tag、deploy 或發布 Firebase Rules。
- 部署後必須實際檢查正式網站，不只看 CI 或命令結果。

## D-014：官方型錄與競賽統計獨立更新

- 週排程是 repository 之外的運作設定。未經明確授權，Codex 與 Claude 不得執行、重建、修改或取代。

## D-015：舊收藏的手動內容優先保留

> 狀態：**已實作，待正式部署**（Phase 2，2026-10-29，本機工作樹未 commit）。正式網站在部署前仍為舊行為，尚未受到此保護。

### 已確認的正式資料政策

- 只有 `stockAutoFilled` 明確為 `true` 的收藏，才可依官方型錄自動升級。本站自身儲存的字串 `"true"` 視為同一個明確標記；其他任何值都不是。
- `stockAutoFilled` 為 `false`、缺少、無效或無法判定時，一律保留原始內容，不得自動升級，也不得補成 `true`。
- 不得只因型號唯一匹配、零件名稱相似或其他推測，把手動資料視為自動填入。
- 只有使用者明確選擇官方商品，或原資料已有明確自動填入標記，才可套用官方配置。
- 不執行任何收藏批次 migration；未來若需要升級或復原流程，必須另行核准。

### 目前程式實作（本機工作樹，待部署）

- `chooseStockProductForStoredItem()` 與 `upgradeStoredStockItem()` 先檢查 `isExplicitStockAutoFilled()`；未明確為 `true` 的收藏不選任何型錄商品、不改內容、不計入自動回寫。
- 明確自動填入的收藏：有 `stockRecordId` 時只以 recordId 識別（BX-00、CX-00 等共用型號），recordId 已不存在於型錄時不改用型號推測；沒有 recordId 的舊自動資料，只有型號唯一對應一筆商品時才升級，多筆候選一律不處理。
- 手動新增的收藏會寫入 `stockAutoFilled: "false"`；從官方型錄選擇的商品維持 `stockAutoFilled: "true"` 與 `stockRecordId`。
- 收藏列保留本頁不管理的欄位（使用者自訂欄位、`stockAutoFilled: false` 等 falsy metadata），存檔時原樣寫回。
- 管理員唯讀檢視 `user-view.js` 採相同規則，手動收藏顯示原始資料。
- 自動升級後的 `saveData()` 仍受 Phase 1 的 ready、UID、generation、readonly 防護；cache snapshot 不會觸發寫入。
- 行為測試：`tests/collection-autofill-safety.test.mjs`（實際執行 `script.js`／`user-view.js` 程式與正式型錄 JSON，含 mutation 檢查）。

### 尚未處理與殘留風險

- 部署前正式網站仍會改寫手動收藏；若部署延後，期間開啟主頁的使用者仍可能受影響。
- 過去可能已被舊版改寫的收藏，本階段不辨識、不復原；需要歷史備份才能比對，另案授權處理。
- `stockAutoFilled` 若為非字串的 truthy 值（例如數字 `1`），使用者之後手動存檔時會以字串形式寫回；值本身不會被視為 `true`。

## D-016：競賽統計歷史快照保留於 Git

- 日期化競賽統計 JSON 必須保留在 Git 專案中；新版統計新增快照，不覆蓋或自動刪除既有歷史快照。
- 不另建與現有 canonical 主資料及競賽統計契約互不相干的第二套統計資料庫。
- 現有匯入腳本尚未依此決策調整；修改腳本與對應測試必須另立任務。

## D-017：賽事並行寫入使用 Transaction 與單場賽事衝突檢查

> 狀態：**已實作，待使用者驗收與部署**（Phase 4B 與 4B-1 安全補強，2026-10-29，本機工作樹未 commit）。正式網站在部署前仍是舊行為（整份 `tournamentRecords` 後寫者覆蓋）。

### 已確認的決策（使用者核准）

1. 離線時不允許儲存賽事資料，也不建立離線寫入佇列或背景補送。
2. 網路中斷、交易失敗或衝突時，必須明確告知「沒有儲存」。
3. 尚未提交成功的表單內容必須保留，避免重新輸入。
4. 同一場賽事即使修改不同對局，也視為衝突。
5. 不自動合併同一場賽事的並行變更。
6. 不允許最後寫入者無聲覆蓋其他分頁或裝置的資料。
7. 不修改 Firestore Rules。
8. 不修改 Firestore Schema；`tournamentRecords` 仍是 `users/{uid}/appData/main` 內的陣列。
9. 不拆分 `tournamentRecords` 到其他文件或集合。
10. 不影響 Phase 1～3 的 Session 安全保護。

### 目前程式實作（本機工作樹，待部署）

- `tournament-sync.js`（純函式，無 Firebase／DOM）：`createTournamentOperation()` 建立凍結的操作描述，新增用的 ID 與 `updatedAt` 在交易外產生一次；`applyTournamentOperation(latestRecords, operation)` 只修改目標賽事，其他賽事保留原物件，不修改傳入陣列。
- 衝突規則：修改／對局／回合操作比對目標賽事與操作開始時的基準指紋，不同即拒絕（同場不同對局也算）；目標已不存在回報「已刪除」；刪除時若已有新變更則拒絕刪除；同一 ID 重複出現或 `tournamentRecords` 不是陣列時拒絕寫入。
- `tournament.js` 十個寫入操作全部改為：建立操作 → 交易內讀取最新文件 → 套用 → 只以 `transaction.update` 寫入 `tournamentRecords` 與 `updatedAt`。文件不存在時，只有看見「不存在」的那次嘗試才以 `transaction.set` 建立。已移除 `setDoc` 與 `saveTournamentData()`。
- 記憶體與畫面只在交易成功後以交易讀到的最新文件更新；失敗時不修改正式記憶體。
- Session：每次操作固定使用開始時的 UID、文件參照與 generation；每次嘗試前、callback 讀取前後、完成後都檢查。已送出的 commit 無法取消，但文件參照固定為原帳號且 Rules 只允許本人寫入，不可能跨帳號寫入。

### 4B-1：交易重試、冪等與提交結果（Phase 4C 審查後補強）

- Firebase Web SDK 11.2.0 的 `runTransaction` 預設會自行重試，且重試前看不到 commit 失敗的原因，無法分辨「版本衝突被拒」與「已寫入但回應遺失」。因此 `tournament.js` 以 `runTransaction(..., { maxAttempts: 1 })` 每次只做一次嘗試，由 `startTournamentTransaction()` 自行重試（最多 5 次，間隔 0.3／0.6／1.2／2.4 秒），並依 SDK 相同規則判斷可重試錯誤。
- 每次重試都重新讀取並套用，不會重複套用同一操作：
  - 新增比賽、對局、直接晉級、回合：以操作自己的固定 ID 辨識；最新資料已有該 ID，就是這次操作已寫入（「已確認已提交」），不再寫入。新增比賽即使之後被其他裝置修改，也依 ID 視為已存在，不建立第二場。
  - 修改、完成、刪除等沒有自身 ID 的操作：最新資料若剛好等於「基準套用這次操作後的結果」，不再寫入，但只顯示「雲端資料已是這次要儲存的內容」，不宣稱由這次操作寫入。
  - 其餘差異一律仍為同場衝突，衝突保護未放寬。
- 提交結果三分類：
  - 已確認已提交：交易成功，或以操作 ID 證明已存在。
  - 已確認未提交：沒有任何一次嘗試送出含寫入的 commit；或 commit 被版本衝突、權限等明確拒絕；或逾時時尚未送出任何 commit（之後的嘗試會被停止）。
  - 提交結果不明：曾有含寫入的 commit 因 `unavailable`、`deadline-exceeded`、`internal`、`unknown`、`cancelled` 失敗，或逾時時 commit 仍在送出中。此時一律不說「沒有儲存」，先重新讀取確認；有操作 ID 證據才顯示已確認，內容相符只顯示「雲端資料已包含這次的變更內容（無法確認是否由這次操作寫入）」。
- 草稿：
  - 修改對局草稿保存基準值與使用者輸入；重新開啟時未修改欄位用雲端最新值，雙方都改過的欄位列出並要求選擇，重新提交前需確認。
  - 修改比賽 dialog 衝突時，未修改欄位更新為最新值，雙方都改過的欄位逐一列出。
  - 延遲完成的交易只清除它自己送出的草稿，使用者等待期間的新輸入不會被清除。
- 完成狀態：修改比賽只有在「對已完成的比賽開啟修改」時才重新開啟（`isFinished: false`）；一般修改基本資料不改完成狀態，其他裝置完成後重新儲存也維持已完成。
- 新增比賽結果不明後，同內容重送沿用同一 ID；內容不同時，必須使用者明確確認才建立另一場新比賽。
- 賽事頁顯示「賽事儲存版本：4B-1（交易保護）」，由新版 `tournament.js` 寫入；舊版程式不會顯示此行。
- 測試：`tests/tournament-sync.test.mjs`、`tests/tournament-page-sync.test.mjs`、`tests/tournament-sync-regression.test.mjs`。`tests/helpers/mock-firestore.mjs` 依 SDK 4.7.6 `TransactionRunner` 的重試規則模擬（可重試代碼、同步例外不重試、版本前提、回應遺失、斷線恢復、`maxAttempts`），但不能取代真實 SDK／Emulator 驗證。

### 部署前必須遵守（H2：舊版分頁）

舊版 `tournament.js`（f9c9ea8 以前）以 `setDoc` 整份覆寫 `tournamentRecords`。新版交易無法阻止其他用戶端的寫入；在不修改 Rules 或 Schema 的前提下，沒有可靠的方法阻擋舊版寫入。部署程序：

1. 部署前以 Phase 2.5 備份工具做一份完整快照。
2. 選擇沒有比賽正在進行的時段作為部署窗口；窗口期間不編輯賽事。
3. 部署前，在所有裝置與瀏覽器（含手機背景分頁、主畫面捷徑／PWA）關閉所有賽事頁。
4. push 後等待 GitHub Pages 完成部署；每台裝置重新開啟賽事頁並確認看到「賽事儲存版本：4B-1（交易保護）」，看不到就重新整理，仍看不到則不在該裝置編輯。
5. 所有裝置確認後才恢復編輯；之後若在任何裝置看到沒有版本列的賽事頁，關閉它，不在上面操作。
6. 部署後抽查賽事筆數與備份快照一致。

等待時間無法保證所有舊分頁失效：沒有 Service Worker，但已開啟的分頁會一直執行舊程式，直到被關閉或重新載入。

### 尚未處理與殘留風險

- 舊版分頁（H2）：被遺忘的舊分頁仍可能整份覆寫賽事資料，只能靠上述程序與備份降低風險。
- 主頁（`script.js`）與賽事頁共用同一文件，主頁寫入會讓賽事交易重試；5 次仍失敗會提示沒有儲存。
- 沒有即時監聽：其他裝置的變更要在下一次儲存或重新載入時才會顯示。
- 修改、完成、刪除類操作在「提交結果不明」且其他裝置又改了同一場時，只能顯示結果不明，無法證明是否由這次操作寫入（沒有 Schema 層級的操作識別）。
- 真實 SDK 行為尚未以 Firebase Emulator 驗證；本環境無法下載 Emulator，需在使用者本機以 `demo-` 專案進行。

## D-018：主頁收藏資料以資料表為單位的 Transaction 與衝突檢查

> 狀態：**已實作，待使用者驗收、Emulator 驗證與部署**（Phase 5B-2A；Phase 5B-2B 獨立審查後於 5B-2C-1 修正 F-01～F-03，2026-10-30，本機工作樹未 commit）。正式網站在部署前仍是舊行為（`saveData()` 以 `setDoc(..., { merge: true })` 整欄寫入四個資料表，後寫者覆蓋；Phase 5A 的 R2）。

### 規則

1. 主頁（`script.js`）只寫入與載入時不同的資料表（`beybladeTable`、`partTable`、`configTable`、`historyTable`），外加 `ownerUid`、`ownerEmail`、`updatedAt`。不寫入、不讀改 `tournamentRecords` 或其他欄位。
2. 每次儲存在 transaction 內讀取最新文件，逐表比較：
   - 雲端仍是本頁建立畫面時的版本（基準）→ 寫入。
   - 雲端已等於這次要寫入的內容，**而且本頁有證據是自己寫入的** → 視為已完成，不重複寫入。證據只有三種：本頁送出、結果不明的提交（記錄該表與確切內容）；同一次儲存流程中結果不明的嘗試；自動型錄升級產生的確切內容（兩個分頁同時升級）。沒有證據時，相同內容也可能是其他裝置自己的操作（例如兩台裝置各新增一筆相同零件），一律視為衝突，不無聲判定成功（F-01）。
   - 其他情況 → 衝突。只要有一個表衝突，這次儲存**完全不寫入**（例如刪除配置會同時新增歷史，兩表必須一起成功）。
3. 衝突以資料表為單位：同一個表即使改的是不同筆，也視為衝突（不自動合併同表的並行變更）；不同表的並行變更會自動保留雙方。
4. `updatedAt` 只作顯示與排序，不作為衝突判斷依據。
5. 離線不排隊：transaction 需要伺服器，離線時直接失敗並保留畫面上的變更；恢復連線（伺服器 snapshot 再次到達）後自動重試，重試同樣經過第 2 點的檢查。
6. 衝突、離線、結果不明時，畫面上的變更與已開啟的編輯器都不會被清除；期間收到的雲端更新先暫存，不重建畫面。
7. 衝突時寫入操作停用，使用者在「雲端同步」區選擇：
   - 「載入雲端最新資料」：衝突的表改為雲端版本（捨棄這些表的未儲存變更），其他表的未儲存變更保留並重新儲存。需確認。
   - 「以我的版本覆蓋」：以畫面上的衝突表覆蓋雲端版本。需確認，屬使用者明確選擇的覆蓋。
8. 不修改 Firestore Rules、Schema；不新增操作識別欄位。

### 實作

- `collection-sync.js`（純函式，無 Firebase／DOM）：逐表指紋、變更表判定、`planCollectionCommit()`（write／already／conflict／removed）、`startCollectionTransaction()`（`maxAttempts: 1` 單次嘗試，自行重試 5 次，間隔 0.3／0.6／1.2／2.4 秒，與 D-017 相同的可重試與結果不明代碼）、`classifyCollectionSaveFailure()`、`createCollectionSyncTracker()`（記錄雲端基準、畫面基準、可接受的基準指紋、自己剛取代的舊版本）。
- 兩種基準：雲端基準是上次套用或寫入的雲端原始資料；畫面基準是套用後從畫面收集的資料，用來避免顯示正規化（例如型號格式）被誤判為修改。D-015 型錄升級以「強制變更」標記，經同一 transaction 寫入。
- 狀態流程（`document.body.dataset.collectionSync`）：`clean` → `saving` → `clean`／`pending-network`（確認沒有寫入：離線、權限、逾時前尚未送出）／`pending-unknown`（commit 已送出但結果不明）／`conflict`。`#collectionSyncNotice` 顯示說明與「立即重試」「載入雲端最新資料」「以我的版本覆蓋」。同一次失敗只跳出一次 alert，自動重試只更新提示。
- 結果不明：送出過的內容會加入可接受基準；之後重試若雲端等於該內容即視為已完成，使用者在等待期間再新增的內容會接續寫入，不誤判為衝突。15 秒逾時；逾時後若 commit 仍在途中，之後完成時會自動重試確認。
- Session：每次儲存固定開始時的 UID、文件參照與 generation；transaction 讀取前後檢查。帳號切換或登出會重設追蹤狀態；同一帳號「重新載入」會保留未儲存的變更與追蹤狀態。若 Session 在儲存途中失效（斷線、重新載入），同帳號保留變更並在伺服器恢復後重試。
- 舊畫面保護（F-02）：本頁剛寫入後，若收到內容等於寫入前版本的 snapshot，先保留畫面，再以 `getDocFromServer` 讀取伺服器確認：伺服器仍是本頁寫入的內容，代表那是延遲的舊快照，忽略；否則是其他裝置真正的更新（包括改回原內容），立即顯示。不使用 `updatedAt` 或裝置時間判斷先後（`updatedAt` 是各裝置 `Date.now()` 與「最新值＋1」的混合，舊版用戶端與其他工具不保證遞增）。伺服器讀取失敗會在 2 秒、4 秒後重試，仍失敗就直接顯示最新收到的雲端資料，不會永久壓制遠端更新；這個退路不寫入任何資料。直接讀取不會解除對監聽延遲舊快照的保護，要等監聽本身收到本頁寫入的內容才解除。
- 管理員切換瀏覽對象（F-03）：本頁還有未確認儲存的變更（含儲存中）時先確認；取消則畫面、Session 與進行中的儲存都不變。確認切換後，進行中的儲存不會顯示「已儲存」。
- 有未儲存變更時，登出需確認，關閉或重新整理頁面會出現瀏覽器離開提示。
- 主頁顯示「收藏儲存版本：5B（交易保護）」；`script.js?v=20261030-phase5b`、`collection-sync.js?v=20261030-phase5b`。
- 測試：`tests/collection-sync.test.mjs`（純函式、S0–S5、邊界情況）、`tests/helpers/manager-page-harness.mjs`（以 VM 執行真實 `script.js` 儲存與 snapshot 程式，搭配 mock Firestore 模擬多裝置）。

### 已知限制

- 同一表不同筆的並行修改會成為衝突，需要使用者選擇（刻意保守）。兩台裝置做出完全相同的結果（例如都刪除同一筆）也會顯示衝突，因為無法證明是哪一台寫入的。
- 回應遺失後，若其他裝置又在同一表上接續修改，本頁只能顯示衝突並註明「先前一次中斷的儲存可能已完成」，無法證明是否由本頁寫入（沒有操作識別欄位）。雲端資料不會被覆蓋。
- 舊版主頁分頁（沒有版本列）仍會以 `setDoc` 整欄覆寫；部署程序比照 D-017：所有裝置關閉主頁、部署後確認版本列。
- 真實 SDK 行為需以 Firestore Emulator 驗證（建議延伸 M01–M10）。

## 現況與舊描述的差異

以下差異已依目前程式碼確認，不應自行「修回」舊描述：

1. **本機資料**：收藏、庫存、配置、歷史測試與賽事目前沒有 localStorage 正式副本；localStorage 只保存主題、側欄等 UI 偏好。正式業務資料由 Firestore 保存。
2. **舊 RTDB Rules**：安全封鎖是 Firebase Console 的 deployed 狀態，repository 內沒有 `database.rules.json` 可代表該舊 project。
3. **歷史分析資料**：參考 JSON 仍可能包含 meta／分析 metadata，但正式分析 UI 已退役，競賽統計仍以客觀資料為界線。
4. **Firebase 初始化**：目前多個頁面各自初始化相同 project。這是既有實作，不代表可未經任務重構。
