# 06｜實作階段規劃

## 最大的技術風險：資料是從畫面表格讀出來的

`script.js` 儲存時由 `collectCurrentData()` 讀取 `#beybladeTable`、`#partTable`、`#configTable`、`#historyTable` 的 DOM 列（`script.js:1552-1617`），而不是從記憶體中的資料模型。D-018 交易的「畫面基準」也是從這些表格收集。所以：

- **不能直接刪掉或改寫這些表格的結構**，否則儲存的內容會改變。
- 新 UI 有兩種接法：
  1. **保留表格作為資料來源（推薦先做）**：四個表格保留在頁面中（可視覺隱藏），新元件讀取表格內容來呈現，所有寫入仍透過既有函式（`addRow`、`addPart`、`addConfig`、`deleteRow`、`restoreHistoryRow`…）。資料流與交易完全不變，風險最低。
  2. **改為記憶體資料模型**：把表格換成 JS 狀態，渲染與儲存都從狀態出發。長期較乾淨，但會動到 D-018 的畫面基準收集，屬於核心協定周邊修改，必須獨立審核、完整回歸與 Emulator 驗證。**不列入第一批。**

## 階段

每個階段一個或數個獨立 commit，單獨部署、單獨回退。資料格式在 7-1～7-5 全程不變，所以回退只需 revert 並更新快取版本，不會留下不相容資料。

|---|---|---|---|---|

## 每階段共同驗收

1. 全部 Node 測試、`validate-site`、build、`git diff --check`。
2. 實際瀏覽器：390×844、768×1024、1440×900，深色與米色，無水平 overflow，Console Error 0。
3. 主頁「收藏儲存版本」與賽事頁「賽事儲存版本」文字不變（部署程序依賴它們）；若要改版本號，需同步更新部署程序與測試。
4. 任何觸及寫入路徑的階段，加跑 Emulator（M 系列或 E 系列）。
5. 部署前備份並驗證；部署程序比照 D-017／D-018（關閉舊分頁、確認版本列）。
6. 不改 `collection-sync.js`、`tournament-sync.js`、`data-session-guard.js` 的協定行為，除非該階段明確列為核心修改並經審核。

## 主要風險

| 風險 | 說明 | 降低方式 |
|---|---|---|
| 儲存內容被 UI 改動影響 | 資料從 DOM 表格收集 | 7-1～7-5 保留表格為資料來源；每階段比對儲存前後 `cells` 完全相同 |
| 舊分頁覆寫 | 舊版主頁仍可能以舊邏輯儲存 | 沿用部署程序；7-7 必須兩段式 |
| 規則誤擋合法組合 | 研究未確認的例外 | 只阻擋官方確認的規則；其他只提示；舊配置永不因新規則被擋住開啟 |
| 導覽改變影響習慣 | 底部導覽是既有契約 | 需使用者決定；可保留舊五項 |
| 大量 DOM 改造造成回歸 | `script.js` 約 4300 行綁定大量 id | 逐區替換；每區一個 commit；保留舊 id 或提供相容層 |
| 手機效能 | 收藏與配置數量大時的渲染 | 清單虛擬化或分頁（7-2 評估） |
