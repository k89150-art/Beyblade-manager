# 05｜新功能建議與優先順序

評估欄位：價值（高／中／低）、官方規則（符合／需研究結果／不涉及）、需要的資料、難度（低／中／高）、對現有系統的影響、是否改 Firestore Schema、是否列入第一批。

## 重要前提：哪些資料能加欄位

`collectCurrentData()`（`script.js:1586`）每次儲存都從畫面表格重新組出資料：

- `beybladeTable` 會保留不認得的欄位（D-015 的 `_storedItemExtras`）。
- `partTable`、`configTable`、`historyTable` **只保存 `cells`（與 `mainStockName`）**，其他欄位在下一次儲存時會被丟掉（`getTableData` `script.js:1552-1583`、`getHistoryData` `1599`）。

所以任何「替配置加名稱、星號、標籤、版本」的功能都不能直接寫新欄位：正式網站與舊分頁會在下一次儲存時刪除它們。必須先部署「保留未知欄位」的版本，等所有裝置更新後，才能開始寫新欄位。這屬於 Schema 變更，列在後續階段並需另行審核。

## 可於後續版本新增

| 功能 | 價值 | 說明 | 難度 | Schema |
|---|---|---|---|---|
| **收藏完成度**（依系列對照官方型錄的已擁有型號） | 中 | 用本機型錄計算；限定為「型錄中有幾款已擁有」，不做稀有度評價 | 低 | 否 |
| **缺少零件提示**：想組的配置缺哪個零件、被哪個配置占用 | 中 | 組裝器內提示，可一鍵前往拆解對方配置 | 中 | 否 |
| **個人實戰紀錄**：每個配置出場次數、回合勝負、得分方式分布 | 中 | 只用使用者自己的回合資料，文案限描述性；目前賽事存的是配置文字快照，配置改名後會分散 | 中 | 否（精確對應需配置 ID，見下） |
| **收藏展示模式**（方向 B 的圖卡牆） | 低～中 | 只是另一種檢視 | 中 | 否 |
| **配置名稱、備註、常用星號、標籤** | 高 | 需先部署「保留未知欄位」版本 | 中 | **是**（加欄位） |
| **配置歷史版本** | 中 | 每次修改保存前一版；文件大小會成長，需上限 | 高 | **是** |
| **配置穩定 ID，賽事以 ID 連結配置** | 中 | 讓實戰紀錄不因改名分散；舊賽事保留文字快照 | 高 | **是** |
| **收藏數量欄位**（取代同款多列） | 低 | 現在多列可運作，改動影響庫存計算與 D-015 | 高 | **是** |
| **零件圖片** | 中 | 需確認圖片授權；不可直接使用官方圖片 | 中 | 否（靜態資源） |

## 不建議新增

| 功能 | 理由 |
|---|---|
| Tier 評級、自動配置推薦、推估勝率 | 違反 D-008；已明確移除 |
| 把 MetaBeys 與 Beywatch 百分比合併成單一分數 | 定義不同，不得混算 |
| 依競賽統計替使用者的收藏或配置打分 | 屬主觀推薦的變形 |
| 把「待確認」的組裝規則設為阻擋 | 官方未確認，可能擋住合法組合；只能提示 |
| 本機離線資料副本、離線寫入佇列 | AGENTS.md 與 D-017 已決定不做 |
| 公開分享個人收藏頁 | 需要修改 Rules 與隱私政策，超出本專案的安全範圍 |
